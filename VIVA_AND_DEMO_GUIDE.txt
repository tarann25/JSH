2. HOW TO PROVE jsh IS BUILT FROM SCRATCH (IF TEACHER ASKS:
   "ISME WOHI SAB HAI JO NORMAL TERMINAL SHELL MEIN HOTA HAI?")
--------------------------------------------------------------------------------

If the teacher asks how this is different from a normal terminal shell or
suspects you wrapped system()/Bash, show these 5 proofs live:

Proof 1 — Live OS Syscall & FD Visualizer ('trace on' built-in):
  Unlike a normal shell (Bash/Zsh), jsh has a built-in 'trace on' mode that
  prints every kernel syscall, PID, and file descriptor number in real time!
  Run inside ./jsh:
    trace on
    ls src | grep .c > out.txt
    cd /tmp
    cd -
    trace off
  The teacher literally sees:
    - parse: 2 command stage(s)
    - pipe() [stage 0 -> 1] -> read_fd=3, write_fd=4
    - fork() -> stage[0] pid=... ("ls"), dup2(fd=4 -> STDOUT_FILENO)
    - fork() -> stage[1] pid=... ("grep"), dup2(fd=3 -> STDIN_FILENO),
      open("out.txt", ...) -> fd=..., dup2(..., STDOUT_FILENO)
    - waitpid(...) -> status=0
    - builtin cd: chdir("/tmp") in parent pid=... (no fork!)

Proof 2 — Process Hierarchy Check ('ps'):
  Run inside ./jsh:
    ps -o pid,ppid,comm
  - Shows 'ps' has PPID = jsh (not bash), proving jsh directly forks and
    execvp()s programs itself.

Proof 3 — Prove It Is NOT Calling system() or /bin/sh:
  Run inside ./jsh:
    echo $HOME
  - Bash expands $HOME to /home/<user>.
  - jsh prints '$HOME' literally because our own C parser (src/parser.c)
    tokenizes input directly without env-variable expansion (per Synopsis
    Section 2). If we used system(), /bin/sh would have expanded it.

Proof 4 — Binary Inspection (Zero Shell Libraries, Raw POSIX Syscalls):
  Run from normal bash before/after demo:
    ldd ./jsh
    nm -u ./jsh | grep -E "fork|execvp|waitpid|pipe|dup2|open|chdir|getcwd"
  - Shows ./jsh links ONLY libc.so.6 and calls fork, execvp, waitpid, pipe,
    dup2, open, chdir, getcwd directly—with NO system() or popen().

Proof 5 — Verbal Answer for the Teacher:
  "Externally, a shell must behave like a shell so standard commands work.
   What makes this an OS project is how it works underneath: zero system()
   calls. Our C code manually parses commands, manipulates kernel file
   descriptors with open()/dup2()/pipe()/close(), creates and replaces
   processes via fork()/execvp(), handles SIGINT, and reaps every child via
   waitpid()—which you can watch live using our 'trace on' mode."

4. VIVA QUICK-REFERENCE SUMMARY
--------------------------------------------------------------------------------

A. What did we build?
   jsh, a minimal interactive Linux shell in C11 using raw POSIX system calls
   (getline, fork, execvp, waitpid, open, close, dup2, pipe, chdir, getcwd,
   sigaction).

B. Why do we need a shell?
   Users cannot directly invoke kernel system calls. The shell is the user-space
   command interpreter that translates typed commands into process creation,
   file descriptor redirection, and IPC with the OS kernel.

C. Why build this from scratch & how is it different from Bash/Zsh?
   - Bash/Zsh have huge scripting engines, readline UI, job control, and
     expansions that hide the underlying OS syscalls.
   - jsh is strictly minimal (1,320 lines of core C) and modular (7 modules
     matching Synopsis Sections 5.1-5.7), built purely on POSIX syscalls plus a
     live 'trace on' syscall/FD visualizer for OS lab learning.

D. What is the benefit of this project?
   1. Practical Mastery of OS Internals: Bridges theory and practice by directly
      implementing process lifecycles (fork/execvp/waitpid), IPC (pipe),
      descriptor wiring (open/dup2/close), and signal handling (sigaction)
      without high-level wrappers like system().
   2. Live Kernel-Call Transparency ('trace on'): Unlike everyday shells that
      behave like black boxes, jsh acts as a self-documenting OS lab tool—
      visualizing every PID, file descriptor number, pipe endpoint, and exit
      status in real time.
   3. Lightweight, Auditable & Dependency-Free: Compiles strictly under C11 +
      POSIX linking only libc, making it easy to embed in minimal Linux
      environments, verify for zero FD/memory leaks, and extend module-by-module.

E. Drawbacks / Limitations:
   1. No background jobs (&, jobs, fg, bg, Ctrl+Z).
   2. No variable ($HOME) or wildcard (*.c) expansion.
   3. No command history (arrow keys) or tab completion.
   4. No stderr redirection (2>, 2>&1) or heredocs (<<).
   5. No logical chaining (&&, ||, ;) or shell scripting (if/for).

F. Future Scope:
   1. Background execution (&) with process groups and SIGCHLD reaping.
   2. Raw terminal line editing (termios) for command history & tab completion.
   3. Environment variable ($VAR) and wildcard (glob) expansion.
   4. Conditional operators (&&, ||, ;) and stderr redirection (2>, 2>&1).
   5. Script file execution (./jsh script.sh).
